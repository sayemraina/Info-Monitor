**Client-side compute: Is this genius or does it have hidden downsides?**  
Let me think about this honestly for our specific system, not in the abstract.  
**What World Monitor computes client-side:** CII scoring (weighted averages), geo-convergence detection (spatial binning), signal aggregation, clustering. These are all operations on data that's already been fetched — you pull the events, then compute scores locally. The raw data is small (news headlines, coordinates, event metadata) and the computation is simple math (weighted sums, distance calculations, sorting).  
**What our system computes:** This is where it gets different. Our pipeline has two very distinct phases:  
**Phase A (heavy, must be server-side):** Claim extraction via Claude Sonnet API calls, embedding generation via OpenAI API, HDBSCAN clustering, supply chain temporal matching, lead-lag cross-correlation. These require API keys that can't be exposed to the browser, involve expensive LLM calls, and process raw text that's too large to ship to the client.  
**Phase B (light, could be client-side):** Once claims are extracted, embedded, clustered, and metrics are computed — everything that happens AFTER that is math on structured JSON. Divergence computation (JSD between two vectors), friction ratios, momentum percentile changes, arousal aggregation, source diversity effective count, IFI computation. These are all pure functions on pre-structured data. No API calls. No secrets. Just arithmetic.  
**The honest assessment:**  
For our **demo** (pre-computed cached data), the **entire thing is already client-side.** The JSON files sit in **/data/**, the frontend reads them, done. Zero server cost. This is what we have now and it works.  
For **live operation**, Phase A has to run somewhere — **you need a server (or serverless functions)** that calls Claude Sonnet, generates embeddings, runs HDBSCAN, and **outputs the structured JSON.** That's an unavoidable server cost.   
But it's a **BATCH cost — you run it on a schedule (every 6 hours, every 24 hours), not on every user request. One batch run serves all users.**  
Phase B — everything the user interacts with in real time — CAN run client-side. Ship the pre-computed claims, clusters, and metrics as JSON. The frontend computes divergence between slices on demand (when the user changes the slice selector). Computes IFI from the current window's data. Generates situation alerts from the metrics. All of this is millisecond-level math in the browser.  
**The genius part:** The expensive work (LLM extraction, embedding, clustering) **runs once per batch**. The interactive work (slice comparison, metric exploration, node selection) **runs per-user but costs zero because it's client-side**. You could have 100,000 users simultaneously exploring the same topic's data and your server cost is identical to 1 user — **because the server only runs the batch pipeline, not the exploration.**  
**The hidden downside:** Data size. World Monitor's data is compact — events with coordinates and metadata. Our data is potentially large — a topic with 5,000 extracted claims, each with embedding vectors, engagement metadata, platform source, arousal tags, cluster assignments. If you ship all of that as JSON to the browser, you could be looking at 5-20MB per topic. That's a meaningful page load. Users on mobile or slow connections will wait.  
**The solution is tiered data loading.** Ship the SUMMARY data immediately (cluster-level aggregates, pre-computed metrics, situation alerts, the landscape node positions) — this is maybe 200KB per topic. Ship the DETAIL data on demand (individual claims, example content, full engagement metadata) when the user drills into a specific claim. This is lazy loading. The landscape renders instantly from summary data. The briefing strip renders instantly. When they click a node, you fetch the detail for that cluster.  
**The superior architectural decision:** A hybrid that maximizes client-side without the downsides.  
Batch server (runs on schedule): Ingest → Extract → Embed → Cluster → Compute metrics → Output two JSON tiers: **summary.json** (small, ships immediately) and **detail/{cluster\_id}.json** (per-cluster, loads on demand).  
Client (runs per-user, zero server cost): Loads **summary.json** on page load. Renders landscape \+ HUD instantly. Computes slice comparisons, IFI, situation alerts from summary data. When user clicks a node, fetches **detail/{cluster\_id}.json** for that cluster's claims, provenance, coordination signals.  
This gives you: instant page load (summary is small), zero per-user server cost (all exploration is client-side), and no massive JSON payload (detail loads only when needed). The batch server can be a simple cron job on a $5/month VPS or a scheduled serverless function. It runs every 6 hours, costs pennies, and serves unlimited users.  
**Bottom line:** Yes, client-side compute is the right call for everything after the extraction pipeline. The nuance World Monitor doesn't face (because their data is inherently small) is data size — we solve it with tiered loading. The architecture is: expensive batch (scheduled, runs once) \+ cheap client (runs per-user, scales infinitely).
