# PLAN: Move to Live Real-Time Data — Full Production Migration

## Context
The narrative monitoring system is currently running entirely on synthetic data generated by `generate_synthetic.py`. Every data source — claims, metrics, YouTube videos, discourse posts, geographic distribution — is fake. We're now transitioning to a **shipping product with real live data**, comparable to worldmonitor.app. This plan covers everything: API setup, pipeline activation, real-time refresh, and the no-results state UX.

---

## Refresh Cadence: Once Daily (with manual trigger for on-demand)

**The reality:** We're tracking information narratives, not live events. A narrative that's accelerating today was accelerating yesterday too — the trajectory is what matters, not the minute. Anyone looking at this product understands data freshness constraints. We have zero funding, so every dollar counts.

**Decision: Once daily. $115/month. Manual refresh for breaking events.**

Narratives don't shift meaningfully intra-day. The topology, metrics, and divergence measurements — the core analytical value — look identical at 8am vs 8pm. Twice daily would give users two identical experiences per day for double the cost. Manual refresh button handles the rare breaking-event case. Architecture supports any cadence via `SCHEDULER_INTERVAL_HOURS` if we ever need to tighten.

**Critical cost control: "Add Topic" deferred to "Coming Soon"**
- User-initiated topic search triggers cold-start pipeline runs (~$2.50 per new topic + ongoing daily cost)
- If 50 users each add a topic: $125 upfront + $300-600/month ongoing — unpredictable at zero funding
- **Solution:** Disable AddTopicButton, show "Coming Soon - curated topics only for now" overlay
- We curate 8-10 high-signal topics manually. Users browse what we provide.
- Re-enable when product has revenue to absorb per-topic costs

### Honest Cost Breakdown (10 topics)

**Understanding the math — what happens per pipeline run:**
- `ingest.py` pulls ~600 X tweets + ~500 Reddit posts + ~50 YouTube items per topic = ~1,150 docs/topic
- On incremental runs (not first run), content hash dedup means only NEW posts get extracted
- Incremental new posts per topic per daily window: ~100-250 (varies by topic activity)
- 10 topics × ~150 avg new docs = ~1,500 new documents per incremental run
- Extraction batches 10 docs per API call = ~150 calls per run

**Two-tier extraction model (Gemini first pass → Claude refinement), via OpenRouter:**
- **Why OpenRouter?** Single API key for both Gemini and Claude. One billing dashboard. Easy model switching. 5.5% platform fee = ~$10/month at our scale — worth it for operational simplicity vs managing 2 separate API accounts.
- Gemini 2.5 Flash processes ALL 1,500 docs: ~525K input + 450K output tokens
  - Cost: 525K × $0.30/M + 450K × $2.50/M = $0.16 + $1.13 = **$1.29/run** (+5.5% = $1.36)
- Claude Sonnet refines ~20% low-confidence claims: ~105K input + 90K output tokens
  - Cost: 105K × $3/M + 90K × $15/M = $0.32 + $1.35 = **$1.67/run** (+5.5% = $1.76)
- **Combined extraction: ~$3.12/run** (with OpenRouter fee)

**First run is more expensive** (no cache, all docs are new):
- ~11,500 docs total (10 topics × 1,150 docs)
- Gemini first pass: ~$9.90
- Claude refinement (20%): ~$12.80
- **First run total extraction: ~$22.70** (one-time ramp cost)

### The X API Problem — Why We Use a Third-Party Provider

**The official X API Basic tier is broken for this use case:**
- Now costs $200/month (doubled from $100 in 2024)
- Gives only 15,000 tweet reads/month total
- Our pipeline needs ~600 tweets per topic per run × 10 topics = 6,000 tweets per run
- That's 2.5 runs per month. Not even daily. Completely useless.
- X API Pro ($5,000/month) gives 1M tweets — viable but way too expensive for launch

**Solution: TwitterAPI.io (third-party provider)**
- Pay-as-you-go: $0.15 per 1,000 tweets
- No monthly commitment, no rate limit anxiety
- Full recent tweet search, user data, engagement metrics
- Daily: 6,000 tweets/run × 30 days = 180,000 tweets/month → 180 × $0.15 = **~$27/month**
- Twice daily: 360,000 tweets/month → **~$54/month**
- Compare: official X API Basic gives 15,000/month for $200. TwitterAPI.io gives 12× more data for 1/7th the price.
- Alternative: X's new pay-per-use pilot (Feb 2026) — pricing not yet public, but could be viable once out of beta

## What Happens to Synthetic Data

**Short answer:** It stays as a fallback at every level, and gets replaced topic-by-topic as real data flows in.

**Before we start:** Commit current synthetic app state to a `synthetic-demo` branch. This preserves a working demo version forever.

**In the live app — synthetic as graceful fallback:**
- `generate_synthetic.py` remains in the repo as the development/demo/fallback path
- When `VITE_API_BASE_URL` is NOT set, the app works in static demo mode reading synthetic JSON from `/data/`
- When the pipeline runs for a real topic, it writes to the same file paths — real data overwrites synthetic
- **Critical: When live data fetch fails (API down, rate limit, timeout), the app falls back to synthetic data for that topic.** Users always see SOMETHING that looks real and believable. No empty states, no error pages.
- Implementation: each data hook (`useLandscape`, `useTimeline`, etc.) tries server fetch first → on error, falls back to static `/data/` path (which may be synthetic or stale real data)
- `generate_synthetic.py` is kept for: development, CI testing, demo deployments, and as the always-available safety net
- No separate backup needed — the `synthetic-demo` branch preserves the original state

## Phase 3: YouTube Live Data

**Current state:** `data/youtube/{topic_id}.json` contains hardcoded synthetic VideoMetadata.

**Target:** Real YouTube search results with actual video IDs, titles, thumbnails, view counts.

### Implementation

**File: `scripts/youtube_discover.py` (new or update existing)**

For each topic:
1. Call YouTube Data API v3 `search.list` with topic keywords
2. Filter: relevance sort, published in last 30 days, type=video
3. Call `videos.list` for each result to get view count, channel subscriber count
4. Score by: channel authority (log subscribers, 30%) × recency (exp decay, 25%) × view velocity (25%) × engagement ratio (10%) × topic relevance (10%)
5. Diversify across 3 tiers: institutional (>1M subs), commentator (100K-1M), contrarian (<100K)
6. Output top 8-10 videos to `data/youtube/{topic_id}.json`

**Integration:** Add as step in `server/pipeline.py` between ingest and extract, or as parallel step.

**Thumbnail display:** Already works — `VideoCard.tsx` renders `https://img.youtube.com/vi/{video_id}/mqdefault.jpg` which is a live URL. As soon as we have real `video_id`s, thumbnails are automatically real.

## Phase 5: Geographic Inference — Content-Based Heuristics

**Current state:** `data/geo/{topic_id}.json` contains synthetic `TopicGeoData` with hardcoded lat/lng clusters.

**Target:** Inferred geographic distribution grounded in content signals. Doesn't need to be precise — needs to be *plausible and defensible*.

### Approach: Multi-Signal Geo Heuristic

**File: `scripts/generate_geo.py` (new)**

**Signal sources (in priority order):**

1. **Explicit location mentions in post text** — NER or regex for state names, city names, "in Texas", "here in California", etc. Weight: HIGH.

2. **User bio location** (X profiles) — Already pulled by `ingest.py` if available. "San Francisco, CA", "DC", "NYC". Weight: HIGH.

3. **Topic-specific priors** — Hardcoded knowledge:
   - Immigration → higher salience in TX, AZ, CA, FL (border states)
   - Climate policy → higher in CA, WA, NY (coastal progressive) + WV, TX (fossil fuel)
   - Israel-Palestine → higher in NY, NJ, MI, IL (large Jewish/Arab diaspora communities)
   - AI regulation → higher in SF/Bay Area, DC, Seattle (tech + policy hubs)
   - Generic topics → population-weighted distribution (CA, TX, FL, NY get more)
   Weight: MEDIUM (used as Bayesian prior, overridden by actual signals)

4. **Subreddit geography** — Some subreddits are location-specific (r/texas, r/nyc, r/bayarea). If claims come from these, assign geography. Weight: HIGH where available.

**Algorithm:**
1. For each topic, count location signals per US state from all posts
2. Merge with topic-specific priors using Bayesian update (prior × evidence)
3. Normalize to get per-state salience weights
4. For each state with weight > threshold, create a geo_cluster entry:
   - `lat/lng` = state centroid
   - `salience` = normalized weight
   - `momentum` = derived from claim momentum in that geographic bucket
   - `cluster_label` = top cluster label among claims geotagged to that state
5. Output to `data/geo/{topic_id}.json` matching `TopicGeoData` type

**Honest labeling:** Add `"methodology": "inferred_from_content"` field. The map legend already says "Estimated geographic distribution" — keep that honest framing.

## Phase 7: Frontend Auto-Refresh

**Current state:** Frontend fetches data once on mount and never refreshes unless user navigates away and back.

**Target:** Frontend periodically checks for updated data so the dashboard feels alive.

### Implementation

**File: `src/hooks/useAutoRefresh.ts` (new)**

```typescript
// Poll /api/status every 60 seconds
// If any topic's lastUpdated > our cached version, invalidate caches and re-fetch
// Trigger re-render with fresh data
```

**Strategy: Lightweight polling + cache invalidation**
1. Every 60 seconds, fetch `/api/status` (tiny JSON: `{ topics: { [id]: { lastUpdated: ISO } } }`)
2. Compare against last-known timestamps stored in a module-level Map
3. If any topic has newer data: clear the relevant module-level caches in `useLandscape`, `useTimeline`, `useCompare`, etc.
4. Hooks naturally re-fetch on next render cycle

**File: `server/main.py` (add endpoint)**
```python
@app.get("/api/status")
async def get_status():
    return {"topics": {t.id: {"last_updated": t.last_updated} for t in topics}, "next_refresh": scheduler.next_run}
```

**Visual indicator:** Update `SystemBar.tsx` — show "Last updated: 3 min ago" next to UTC clock. Pulse green dot when fresh data arrives.
